# AI Worklog — контент для вставки в приложение

## Инструменты

- **Claude (Claude.ai, Sonnet 5)** — помощь с архитектурой и промптами:
  проектирование модели данных и формулы подбора, декомпозиция на этапы,
  ревью каждого диффа перед принятием, помощь с git/окружением, финальный
  сбор этого Worklog.
- **Claude Code CLI (модель claude-sonnet-5, claude-haiku-4-5)** —
  непосредственная реализация: каждый из 7 промптов выполнялся им
  в VS Code, с git-коммитом после каждого шага.

Суммарно за компьютером — около 6 часов вперемешку с перерывами, включая
финальный прогон `/ultrareview` и фикс найденного.

## Промпты и решения

Промпты подавались по одному на этап.

**3-5 решений, принятых самостоятельно:**
1. Выбрал тему «Бюро переселения привидений» и спроектировал модель
   данных: поля заявок и мест, список из 7 особых условий, шкалу
   освещения/влажности 1-5.
2. Заменил дедлайн-строку на номер игрового дня + кнопку «Следующий
   день →» вместо тикающего таймера — чтобы демонстрировать просрочку по
   клику, без ожидания.
3. Разделил единый документ-спеку на три отдельных файла (контекст для
   себя / техническая спека для проекта / промпты).
5. После code review отобрал из 9 находок 4 критичных для правки (статус
   заявки не пересчитывался при смене дня и при чужом assign/clear)

## Ошибки AI и доработки

- Один `git commit` без `-m` завис на пустом сообщении в редакторе — Claude
  Code сам это заметил и на следующем шаге создал коммит со своим
  сообщением по шаблону «шаг N».
- Изначально `Place` получил два поля под одну и ту же классификацию места
  (`type` свободной строкой и `propertyType` как enum) — заметил дублирование
  и попросил объединить в одно поле.
- После снятия размещения с просроченной заявки причина отказа переставала
  быть видна в общем списке (хотя оставалась в карточке деталей) — асимметрия
  в отображении `unplaceable` против `placed`-конфликта, исправлено отдельным
  уточнением перед шагом 5.
- Финальный `/ultrareview` нашёл более серьёзный системный баг: статус
  заявки хранился в состоянии и пересчитывался только у той заявки, которую
  трогаешь напрямую — смена дня или освобождение места чужой заявкой не
  обновляли статус остальных. Причина — логика статуса была продублирована
  в трёх компонентах вместо одной общей функции. Попросил вынести единую
  точку правды и переиспользовать её везде.
- Тот же ревью нашёл смешение «дедлайн просрочен» и «конфликт по атрибутам
  места» в одном и том же поле причины — из-за этого уже размещённая заявка
  с истёкшим дедлайном показывала предупреждение о конфликте с местом,
  хотя место тут ни при чём. Дедлайн — свойство заявки, а не места; попросил
  завести отдельную функцию `roomConflictReason` только для реальных
  атрибутов места (чердак/зеркала/люди/шум/свет/влажность/вместимость) и
  использовать её для уже размещённых заявок, а полный список фильтров
  (включая дедлайн) оставить только для расчёта unplaceable у ещё не
  размещённых.

**Что улучшил бы, если бы это был реальный продукт:**
- Настоящую персистентность вместо состояния в памяти (сейчас обновление
  страницы всё сбрасывает)
- Полноценную форму создания новых заявок/мест (осознанно вынесена за
  скоуп тестового)
- E2E-тесты поверх UI-сценариев (сейчас юнит-тесты покрывают только чистую
  логику подбора и валидацию данных, не сами компоненты)
- Разделить единый механизм «предупреждение, не бан» для переполнения и
  для конфликта условий на два разных правила, если продукту потребуется
  более строгий контроль вместимости
- Синхронизировать выбор в `<select>` карточки заявки с быстрым назначением
  места — единственный найденный code review пункт, который сознательно
  оставил как есть
